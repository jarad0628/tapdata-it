# TapData 集成测试用例计划（L0-L3，组件视角）

> 版本：v2.0（v1.0 为框架级总纲，本版按"产品组件 × 测试分层"重新组织，每个用例描述**测试目的与测试方法**并给出工作量预估，用于排期预测）
> 关联文档：[tapdata-it.md](./tapdata-it.md)（测试建设总纲）、[connector-it.md](./connector-it.md)、[engine-it.md](./engine-it.md)、[tapdata-connector-it-architecture.md](./tapdata-connector-it-architecture.md)
> 代码契约基线：`tapdata-wiki/03_代码说明书/`（36 引擎条目 + 4 连接器条目）

**分层定义（本计划口径）**：

| 层次 | 定义 | 载体 | 责任方 |
|---|---|---|---|
| L0 | 当前代码中已存在的单元测试 | 各仓库 `src/test`（`*Test.java`） | 开发者 |
| L1 | 单 Module 集成测试：各 Connector 按接口测能力（继承 [ConnectorIT](../tapdata-connector-it/src/main/java/io/tapdata/it/ConnectorIT.java)）；引擎、管理端、API Server 等组件的独立集成测试 | `tapdata-it` 聚合工程 + 各仓库 `src/test`（`*IT.java`） | 开发者 |
| L2 | 面向产品能力的集成测试：跨 Module 交互（WebSocket 通信、任务调度、Connector 更新与自动加载、模型管理、通知告警、监控指标暴露等） | `tapdata-it` + 各仓库（`*IT.java`，内存级/Spring Context） | QA/SDET 主导 |
| L3 | 完整产品黑盒测试：运行完整产品，执行 HA、Failover、生产稳定性等用例 | `t-layer3-test` 或者其他 | QA/SDET 主导 |

## 一、产品组件全景与功能

TapData 是多模块数据集成/实时 CDC 平台，产品运行时组件及功能如下（依据 tapdata-wiki A-20260813-仓库拓扑 与代码盘点）：

| 组件 | 代码位置 | 核心功能 | 集成测试关注点 |
|---|---|---|---|
| **执行引擎 iengine** | `tapdata/iengine`（iengine-app / iengine-common / iengine-oss / modules / validator） | 任务执行：DAG 编译、任务调度（`TapdataTaskScheduler`）、全量读取（三条路径）、增量读取（offset/断点）、目标端写入（写入策略/exactly-once）、DDL 同步、ShareCdc 共享挖掘、分区分片并发保序、指标上报 | 任务生命周期、数据一致性、断点续跑、事件不丢不重 |
| **管理端 TM** | `tapdata/manager`（tm / tm-api / tm-common / tm-oss；企业版 tm-enterprise） | 控制面：112 个 REST Controller——数据源与连接管理（ds）、连接器/插件版本管理（PdkController/PdkVersionController）、任务与调度（scheduleTasks/taskhistory）、数据校验（inspect）、告警（alarm/alarmrule）、类型映射（typemappings）、外存（externalStorage）、共享 CDC 管理、WebSocket 通信、监控指标（metrics） | API 契约、状态机流转、跨服务联动 |
| **API Server** | `apiserver`（Java 实现，`server_api_definition.json` 定义开放 API；企业版另有 Node.js 实现，`conf.apiServerJar` 切换） | 对外开放 REST API，供第三方系统管理任务/数据源 | 开放 API 契约、鉴权 |
| **PDK 插件层** | `tapdata-common-lib/plugin-kit`（tapdata-pdk-api / tapdata-pdk-runner） | 连接器接口契约（`TapConnector`/`ConnectorFunctions`）与运行时（`TapConnectorManager` 加载/卸载连接器 jar） | 契约稳定性、插件热加载 |
| **连接器** | `tapdata-connectors/connectors`（80+ 开源）、`tapdata-connectors-enterprise/connectors`（DB2/达梦/GBase 等） | 各数据源读写/CDC/建表等能力实现 | PDK 能力函数行为（L1 主战场） |
| **Agent** | `tapdata-enterprise/tapdata-agent`（Node.js） | 进程编排：拉起/守护 apiserver、引擎等子进程 | 进程编排、崩溃恢复（L3 覆盖） |
| **License 客户端** | `tapdata-license/tapdata-license-client` | License 校验与能力开关 | 校验行为（随 L2 抽测） |
| **Hazelcast（fork）** | `tapdata/Hazelcast`（分支 release-v5.5.0） | 引擎分布式底座：集群协调、分布式数据结构 | HA 行为（L3 覆盖） |
| **前端 tapdata-web** | `tapdata-web`（Vue，pnpm workspace） | 用户界面 | 不单独测试，经由 L3 黑盒覆盖 |

**组件间协作链路**（决定 L2 测试域）：前端/WebSocket → TM（任务编排）→ 引擎（执行）→ PDK → Connector → 数据库；TM 经 `scheduleTasks` 下发任务、引擎回报状态与指标（taskhistory/metrics）；PdkController 管理连接器 jar 的上传与热加载。

## 三、L1：单 Module 集成测试

执行环境：组织级自托管 GitHub Actions runner（`docker/docker-compose.yaml` 编排，label `tapdata-it`，4 副本，privileged + docker.sock 挂载）；测试数据库由 Testcontainers/ConnectorIT 在用例中动态拉起、用完销毁。命名 `*IT.java`，`mvn verify` 执行（Failsafe）。

### 3.1 Connector 集成测试（框架已就绪，主战场）

`tapdata-connector-it` 模块已实现通用框架：[ConnectorIT.java](../tapdata-connector-it/src/main/java/io/tapdata/it/ConnectorIT.java)（2624 行）提供 **74 个通用用例**（`should_*`），任何 Connector 只需继承并实现 `createContext()` 即可全量运行。三条可靠性原则：旁路验证（用对端数据源验证写入事实，禁止用 read 验证 write）、动作唯一（一个用例只测一个 function）、声明式能力（`requiredCapabilities()` 声明必实现 + 框架级覆盖校验用例 `should_all_capabilities_implemented_and_covered`）。

74 个用例按功能域归纳为 10 组核心用例（每组即一类集成测试场景）：

| # | 用例组（代表用例） | 测试目的 | 测试方法 | 预估 |
|---|---|---|---|---|
| L1C-01 | 连接与元数据（`should_test_connection`、`should_discover_schema_of_created_table`、`should_connection_check` 等 8 例） | 验证连接凭据校验、表发现与 TapType 类型映射、连接诊断项符合契约 | 预置正确/错误凭据分别调用 connectionTest/connectionCheck，断言 TestItem 项与错误信息；随机建表后调 discoverSchema，对照 TestTableSpec 断言字段类型 | 0.5 天/连接器 |
| L1C-02 | 建表与表 DDL（`should_create_table_v2`、`should_clear_table`、`should_drop_table`、`should_alter_table_charset/ttl` 等 7 例） | 验证目标端 DDL 能力（建表/清表/删表/字符集/TTL/时区）结果正确且幂等 | 旁路直连对端数据源核对 DDL 后的表结构、字段类型映射；对已存在表重复建表验证幂等分支 | 0.5 天/连接器 |
| L1C-03 | 写读一致性（`should_write_insert_records`、`should_batch_read_data_consistent`、`should_write_update_records`、`should_write_delete_records`、`should_batch_count_match`） | 验证全量读取与写入的数据一致性（条数、字段值、类型精度） | 生成类型受控随机数据（RandomDataFactory）写入→旁路读回逐行比对（RecordAssert）；batchRead 回读断言与源端行数/内容一致 | 1 天/连接器 |
| L1C-04 | 条件查询（`should_query_by_filter`、`should_query_by_advance_filter`） | 验证过滤查询与高级过滤（聚合/排序/分页）返回正确 | 预置已知数据集，构造 TapFilter/TapAdvanceFilter 调用并断言命中行 | 0.5 天/连接器 |
| L1C-05 | 增量读取（`should_stream_read_incremental`、`should_stream_read_one_by_one`、`should_stream_read_multi_connection`、`should_timestamp_to_stream_offset`） | 验证 CDC 增量事件（Insert/Update/Delete）、单条消费、多连接并发消费、时间戳转 offset | 容器预置 Binlog=ROW/WAL/Oplog；写入增量数据后调 streamRead，收集事件断言类型与值；断开重连验证续读 | 2 天/连接器（CDC 复杂度高） |
| L1C-06 | 事务与写入控制（`should_transaction_commit`、`should_transaction_rollback`） | 验证事务 begin/commit/rollback 的原子性语义 | 事务内写入多行后 rollback，旁路断言目标端无数据；commit 后断言全部可见 | 0.5 天/连接器 |
| L1C-07 | 索引与约束（`should_create_index/query_indexes/delete_index`、`should_create/query/drop_constraint`、外键 3 例） | 验证索引/约束/外键的创建、查询、删除行为 | 调用对应 Function 后旁路核对元数据定义；外键用例含辅助父表清理（dropForeignKeyAuxTable） | 1 天/连接器 |
| L1C-08 | 字段 DDL（`should_new_field`、`should_drop_field`、`should_alter_field_name/attributes`） | 验证字段级 DDL（新增/删除/改名/改属性）传播正确 | 调用字段 DDL 事件后旁路断言表结构与默认值填充 | 0.5 天/连接器 |
| L1C-09 | 分区表与 offset（`should_create/query/drop_partition_table`、`should_get_read_partitions`、`should_get_stream_offset`、`should_flush_offset`、`should_query_field_min_max`） | 验证分区表支持、分区读取计划、offset 获取与刷新、字段极值查询 | 预置分区父表/子表，调用分区函数断言分片结果；offset 函数配合 streamRead 断点场景验证 | 1 天/连接器 |
| L1C-10 | TapValue 编解码契约（`should_wrap/unwrap_*` 等 14 例 + `should_all_capabilities_implemented_and_covered`） | 验证引擎 TapValue 包装/解包往返不丢值、特殊值（NULL/边界/嵌套/时区）正确、声明能力全部被用例覆盖 | 通过 EngineCodecs 做引擎侧 codec 全链路往返，逐类型断言；框架级校验用例强制 `requiredCapabilities()` 声明与实现的完备性 | 框架内置（0，接入时仅需方言适配） |

**接入排期（首批 6 个高危 CDC 连接器）**：MySQL → MongoDB → PostgreSQL → Oracle → Kafka → Redis；标准接入 1~2 人天/个（复杂 CDC 连接器 3~5 人天）。首批合计约 **10 人天**，MySQLConnectorIT/MongoDBConnectorIT/DB2iConnectorIT 已有接入示例。

> 本章各用例人天均为**纯人工口径**；人+AI 模式下按第六章 6.0 节压缩系数折算（L1 合计约 68 → 38 人天）。

### 3.2 引擎（iengine）集成测试（engine-it 模块，待建）

依据 [engine-it.md](./engine-it.md) 的 D1-D12 维度，在 `tapdata-it` 下新建 `engine-it` 模块：输入 `TaskDto` 配置 + 真实源/目标数据库，经 `HazelcastTaskService` 建 DAG → Jet 执行，断言目标端数据、任务状态、offset 持久化。核心用例 10 个：

| # | 用例 | 测试目的 | 测试方法 | 预估 |
|---|---|---|---|---|
| L1E-01 | 任务启动与 DAG 编译 | 验证 TaskDto → DAG 编译正确、节点按类型（source/processor/target）装配 | 构造 mock→mock 任务启动，断言节点实例化与 DAG 拓扑、任务进入运行态 | 3 天 |
| L1E-02 | 全量同步数据一致 | 验证全量读取→写入链路数据完整 | 源端预置 N 行（多类型字段），启动同步任务后旁路比对目标端行数与内容 | 3 天 |
| L1E-03 | 增量同步与事件类型 | 验证增量 DML 事件按序到达目标端 | 任务运行中在源端执行 insert/update/delete，Awaitility 轮询目标端断言事件与顺序 | 3 天 |
| L1E-04 | 断点续跑 | 验证任务停止/重启后从 offset 续传、不重不丢 | 全量/增量过程中停止任务→源端继续写→重启任务→断言目标端最终一致且 offset 持久化 | 3 天 |
| L1E-05 | 目标端写入策略 | 验证唯一键冲突时按写入策略（insert_on_exists/update/ignore）执行 | 同一任务配置不同写入策略分别运行，冲突场景下旁路断言目标端结果 | 2 天 |
| L1E-06 | 自动建表与类型映射 | 验证无目标表时自动建表、字段类型按映射规则生成 | 源端建表后直接启动任务（不预建目标表），旁路断言目标表结构与类型 | 2 天 |
| L1E-07 | DDL 同步 | 验证 DDL 事件按过滤配置传播/落库（三层闸） | 任务运行中对源端执行 add field/drop field 等 DDL，断言目标端结构变化与过滤规则生效 | 3 天 |
| L1E-08 | 任务停止与状态终态 | 验证停止指令后资源释放、taskhistory 状态为终态 | 运行中下发停止，断言节点关闭、连接释放、状态机进入终态 | 2 天 |
| L1E-09 | 处理器节点（JS/字段加工） | 验证 processor 节点对事件流的加工正确 | 任务含 JS 算子/字段映射/过滤配置，源端写入后断言目标端数据经过处理 | 2 天 |
| L1E-10 | 错误注入与任务级重试 | 验证源/目标故障时任务按重试边界恢复或失败 | 注入网络中断/错误凭据，断言重试次数、退避、最终状态与告警事件产生 | 3 天 |

模块骨架 + 上述用例合计约 **26 人天**（框架复用 connector-it 的 generator/verifier 资产）。

## 六、落地排期与时间预测（人+AI 模式）

### 6.0 人+AI 工作量模型

AI 协同方式沿用 tapdata-it.md 阶段 1 思路：**知识库契约条目（tapdata-wiki）+ 测试模板 + 模块源码作为 AI Context，AI 生成用例初稿，开发者/SDET 人工校准后入库**。压缩系数按工作性质分档（人工校准与真实环境调试无法被替代）：

| 工作类型 | 典型内容 | 压缩系数 | 依据 |
|---|---|---|---|
| 模板化用例生成 | ConnectorIT 接入配置、契约测试、MockMvc 用例、API 用例、数据构造与断言代码 | 50%~60% | 有接入示例/Controller 源码/wiki 契约条目可直接作 Context，AI 初稿可用率高 |
| 联调与框架建设 | engine-it 模块骨架、真实数据库容器联调、跨模块（TM↔引擎）环境搭建 | 30%~40% | AI 生成骨架，真实执行路径问题需人工定位 |
| Flaky 治理与稳定性分析 | CDC 时序伪失败归因、长跑监控、HA 注障演练、集群操作 | 10%~30% | 依赖真实环境观察与经验判断，AI 仅辅助日志分析 |

> 注：压缩系数已包含 AI 生成初稿的时间（分钟级）与人工校准时间；校准成本随知识库校正质量下降（阶段 1 知识库人工校正越准，AI 初稿可用率越高，这也是先建知识库的原因）。

### 6.1 排期表（人+AI 口径）

**人力假设**：2 名连接器/引擎 Dev + 1 名 SDET，每人按 AI 辅助后产能计；执行环境复用自托管 runner（已就绪）。累计约 **76 人天**（纯人工口径约 136 人天，压缩 ~44%）。

| 阶段 | 周期 | 内容 | 工作量（人+AI） | 里程碑出口 |
|---|---|---|---|---|
| P1：L0 收口 + Connector IT 首批 | 第 1 周 | L0 契约测试模板化补齐（~3）；MySQL/MongoDB/PostgreSQL 接入 ConnectorIT（~3） | ~6 人天 | 首批 3 连接器 IT 随 PR 门禁运行 |
| P2：L1 Connector 扩面 + 引擎 IT 启动 | 第 2 周 | Oracle/Kafka/Redis 接入（~3）；engine-it 模块骨架 + L1E-01/02/03（~6） | ~9 人天 | 6 连接器全接入；引擎 IT 首批用例 |
| P3：L1 收口（引擎/TM/API Server） | 第 3-5 周 | L1E-04~10（~10）；TM 基建 + L1T-01~10（~11）；L1A-01~05（~5） | ~26 人天 | **L1 全量完成**（累计 ~38 人天） |
| P4：L2 产品能力 | 第 5-7 周（与 P3 尾部并行） | L2-01~12（WebSocket/调度/热加载/模型/告警/指标等） | ~22 人天 | **L2 全量完成**，纳入 Daily 回归 |
| P5：L3 固化 + CI 门禁 | 第 7-9 周 | nightly.sh 接入 Daily；HA/长跑/断点深度用例；报告汇总与门禁固化 | ~10 人天 | **L3 Daily 全量回归上线** |
| 缓冲 | 第 10 周 | Flaky 治理、覆盖率门禁（≥80%）固化、文档回填知识库 | ~3 人天 | 三层门禁常态化 |

**总体预测：约 10 周（2.5 个月），累计约 76 人天**（纯人工口径约 136 人天 / 14 周；同等人力下日历周期缩短 ~30%）。关键节点：
- 第 1 周末：L1 Connector 首批上线（最快可感知收益）；
- 第 5 周末：L1 全量（单 Module 集成测试体系成型）；
- 第 7 周末：L2 全量（产品能力回归自动化）；
- 第 9 周末：L3 Daily 全量回归 + 三层 CI 门禁常态化。

**排期风险与对策**：① CDC 类 L1C-05/L1E-03/04 工作量波动大——按"容器预置 CDC 配置模板"先行固化（P1 内完成），复杂连接器允许进入 P3 缓冲；② L2-03 热加载涉及 PDK 运行时行为，若发现框架缺口，单独开分支评估（可能触发 PDK 层改造，届时范围上报）；③ 企业版连接器需 `tapdata` 与 `tapdata-enterprise` 平级目录 + `-P enterprise` 构建，环境准备前置到 P1。
